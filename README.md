# Radar Management – B2B Lead Enrichment Microservice

Микросервис для автоматического поиска, сбора и обогащения данных о компаниях через API Checko.
Позволяет по коду ОКВЭД найти организации, получить их контакты, финансовые показатели и сохранить в PostgreSQL.
Предназначен для построения базы потенциальных клиентов («лидов») и последующего скоринга (оценки приоритета) с помощью AI.


## Архитектура

Проект построен по многослойной архитектуре и включает следующие уровни:

- API (роутеры FastAPI);
- веб-слой (Jinja2 Templates + статика, роутер `router_web`);
- сервисный слой (бизнес-логика);
- клиенты внешних API (Checko API, OpenRouter);
- асинхронный слой доступа к данным (SQLAlchemy AsyncSession);
- фоновые задачи (Celery + Redis).
- слой работы с базой данных (SQLAlchemy ORM);
- Pydantic-схемы (валидация и сериализация данных);
- централизованная обработка исключений.

# Основные возможности

* Поиск компаний по ОКВЭД (с фильтром только действующих).

* Сохранение базовых сведений (ИНН, название, статус, ОКВЭД, дата регистрации).

* Обогащение контактами: телефоны, email, веб-сайт, регион.

* Обогащение финансовыми данными: выручка за 2023–2025 годы.

* Опциональная фильтрация компаний по региону при поиске по ОКВЭД.

* Постраничная загрузка компаний из Checko API.

* Автоматический расчёт и сохранение динамики выручки и прибыли в базе данных.

* Приоритизация компаний для первичного холодного обзвона по наличию телефона и финансовых данных, с дополнительной сортировкой по росту выручки.

* Единый эндпоинт /enrich для полного обогащения (контакты + финансы) одной компании.

* Готовые REST API для выборочного обновления и просмотра.

* Строгая типизация API через Pydantic Response Models с автоматической валидацией ответов и документацией Swagger.

* HTTP-запросы (httpx) для высокой производительности.

* Асинхронная обработка запросов (FastAPI + Async SQLAlchemy + httpx.AsyncClient) для неблокирующей работы с базой данных и внешними API.

* **AI-оценка компаний** через OpenRouter – дополнительный аналитический слой для расчёта приоритетности, уровня риска и краткого текстового обоснования.

* Централизованная обработка ошибок внешних API через собственные исключения и глобальные FastAPI exception handlers.

* **Автоматический расчёт динамики роста** – при обновлении финансовых данных рассчитывается процентный прирост выручки и прибыли относительно предыдущего года и сохраняется в БД.

* **Жизненный цикл компании** — поле `progress` со значениями `active`, `archived`, `rejected`, `transferred`. Управление через API и веб-интерфейс.

* **Архивация и восстановление** — компании, отмеченные как обработанные, уходят в архив и не отображаются в основном списке. Доступны на отдельной странице `/web/archive`, откуда их можно вернуть.

* **Массовые действия** — чекбоксы и bulk-панель на страницах веб-интерфейса. Массовая архивация, восстановление, мягкое удаление и экспорт выбранных компаний.

* **Экспорт в CSV** — выгрузка выбранных компаний в Excel-совместимый CSV-файл (UTF-8 с BOM, разделитель `;`). ИНН, телефон, выручка и даты обёрнуты в `="..."` — чтобы Excel не портил длинные номера и не преобразовывал их в научную нотацию.

## Веб-интерфейс

Помимо REST API, проект предоставляет веб-интерфейс на Jinja2 Templates.

Доступные страницы:

- `GET /web/` — главная страница: форма сбора компаний по ОКВЭД и региону.
- `GET /web/companies` — таблица компаний с пагинацией, контактами, финансовыми показателями, динамикой роста и AI-оценкой.
- `GET /web/ranked` — AI-рейтинг компаний (отсортированы по `ai_priority`).
- `GET /web/archived` — архив компаний (со статусом `archived`).
- Кнопки **«AI Score»** и **«Ранжировать»** для запуска AI-скоринга и ранжирования компаний.
- Кнопка **«В архив»** (🗑️ SVG-иконка) в каждой строке — переводит компанию в архив через `POST /companies/{inn}/archive`.

Веб-роутер скрыт из Swagger (`include_in_schema=False`).

Интерфейс использует:

- `app/templates/` — Jinja2-шаблоны (`base.html`, `home.html`, `companies.html`);
- `app/static/` — статические файлы (CSS, JS).

### Массовые действия

На страницах `/web/companies`, `/web/ranked`, `/web/archived` реализованы массовые действия с чекбоксами:

- чекбокс **«Выбрать все»** в шапке таблицы;
- чекбокс в каждой строке;
- панель массовых действий (`.bulk-panel`) появляется при выборе хотя бы одной компании;
- кнопки в панели неактивны (`disabled`), пока ничего не выбрано.

Доступные действия:

- **«В архив»** — массовая архивация (на `/web/companies` и `/web/ranked`);
- **«Вернуть»** — массовое восстановление из архива (на `/web/archived`);
- **«Удалить»** — мягкое удаление с подтверждением (на `/web/archived`);
- **«Экспорт CSV»** — скачивание выбранных компаний в формате CSV.

Вся клиентская логика (чекбоксы, bulk-панель, скачивание CSV, синхронизация скроллбаров) вынесена в единый файл `app/static/js/app.js`, подключаемый через `base.html`.

Все веб-страницы наследуются от `base.html`, который обеспечивает:

- навигацию между разделами **«Главная»** (`/web/`), **«Мои компании»** (`/web/companies`), **«AI Рейтинг»** (`/web/ranked`) и **«Архив»** (`/web/archived`);

Страницы:

- `companies.html` — таблица активных компаний с пагинацией, кнопками **AI Score**, **Ранжировать** и кнопкой архивации в каждой строке.

## Жизненный цикл компаний

Каждая компания в базе имеет поле `progress` — статус её обработки.

Возможные значения (enum `Progress` в `app/models/company.py`):

- `active` — в работе, отображается в основном списке (`/web/companies`).
- `archived` — в архиве, не отображается в основном списке. Доступна на странице `/web/archived`.
- `rejected` — отклонена (не подошла, отказ). Резерв на будущее.
- `transferred` — передана в CRM. Резерв на будущее.

По умолчанию новые компании получают `active`.

Управление статусом:

- `POST /companies/{inn}/archive` — перевести компанию в архив.
- `POST /companies/{inn}/restore` — вернуть из архива.

Все методы репозитория, отдающие список на экран (`get_all_paginated`, `get_all_ranked_paginated`), фильтруют по `progress == Progress.ACTIVE`.
Поэтому архивные компании автоматически исчезают из основного списка и AI-рейтинга.

## Мягкое удаление (soft delete)

Помимо архивации, реализовано **мягкое удаление** компаний — поле `is_deleted` в модели `Company`.

- `is_deleted = False` — компания активна (по умолчанию).
- `is_deleted = True` — компания удалена и **не отображается нигде**: ни в основном списке, ни в архиве, ни в AI-рейтинге.

Физически строка из БД **не удаляется** — только помечается флагом. Это позволяет:

- сохранить историю;
- восстановить данные вручную при необходимости;
- избежать каскадных проблем при удалении связанных записей.

Все методы репозитория, отдающие данные на экран (`get_all_paginated`, `get_all_ranked_paginated`, `get_archive_paginate`, `get_by_inn`, `has_ai_ranked`), фильтруют по `is_deleted == False`.

Удаление доступно только в архиве — через кнопку **«Удалить»** в bulk-панели `/web/archived`.

Метод `save_if_not_exists` при повторной загрузке компании **сбрасывает** `is_deleted = False` — если компания была удалена, но снова найдена через ОКВЭД, она «оживает».
## Счётчики и статистика

На страницах веб-интерфейса отображаются сводные счётчики по компаниям — чтобы пользователь видел картину сразу, без перехода между страницами.

Доступные счётчики:

- **`/web/companies`** — «Активных», «С телефоном», «С финансами», «В архиве».

## Приоритизация компаний

Для первичного холодного обзвона реализована rule-based приоритизация, независимая от AI.

* Priority 1 — есть телефон и выручка за 2024 и 2025 годы.
* Priority 2 — есть телефон, но финансовые данные отсутствуют или заполнены не полностью.
* Priority 3 — отсутствует телефон.

Внутри приоритетной группы компании дополнительно сортируются по `revenue_growth_3` в порядке убывания.

Приоритизация предназначена для выбора наиболее перспективных компаний для первичного контакта и не является оценкой кредитного риска или вероятности банкротства.

##  Динамика роста (growth_calc)

При обновлении финансовых данных для каждой компании рассчитываются и сохраняются два показателя:
- `revenue_growth_3` – процентный рост выручки (2025 vs 2024)
- `profit_growth_3` – процентный рост прибыли (2025 vs 2024)

Функция расчёта `growth_calc(current, previous)`:
- Если `previous` или `current` равны `None` → возвращает `None`.
- Если `previous == 0` и `current == 0`  возвращает `0`.
- Если `previous == 0` и `current != 0`  возвращает `100` (условный бесконечный рост).
- Иначе: `round((current - previous) / abs(previous) * 100, 1)`.

Это позволяет корректно обрабатывать ситуации, когда в предыдущем году показатели были нулевыми или отрицательными.

##  Интеграция с AI (OpenRouter)

Проект использует [OpenRouter](https://openrouter.ai) как единый шлюз к бесплатным и платным LLM.  
Это позволяет:
- Получать аналитические выводы по финансовой отчётности компании.
- Автоматически рассчитывать **скоринг приоритета** (от 0 до 100) на основе выручки, прибыли, динамики роста и региона.
- Генерировать краткое описание компании для менеджеров по продажам.
- AI-скоринг является дополнительным аналитическим инструментом и не заменяет rule-based приоритизацию списка компаний.

### Запуск из веб-интерфейса

AI-скоринг можно запустить прямо из веб-интерфейса:

- кнопка **«AI Score»** на странице `/web/companies` запускает Celery-задачу через `POST /companies/ai_score_all`;
- статус задачи отслеживается фронтендом через `GET /tasks/{task_id}`;
- по завершении страница автоматически перезагружается и показывает обновлённые значения `ai_priority` и `ai_risk`.

## Обработка ошибок

Это обеспечивает:

- собственные исключения для интеграций с внешними API (`CheckoAPIError`, `AiAPIError`, `CompanyNotFoundError`);

## Клиент Checko API

Все запросы к Checko API проходят через единый слой выполнения HTTP-запросов.

Этот слой отвечает за:

- выполнение HTTP-запросов;
- проверку корректности ответа сервера;
- преобразование транспортных ошибок в собственные исключения приложения;
- повторное использование единой логики всеми интеграциями с Checko API.

 ## Асинхронная архитектура

Проект использует асинхронную модель обработки запросов на базе FastAPI и SQLAlchemy AsyncSession.

Асинхронный подход применяется для:

- работы с PostgreSQL через AsyncSession;
- HTTP-запросов к Checko API через httpx.AsyncClient;
- обработки нескольких входящих запросов без блокировки сервера.

Это позволяет эффективнее использовать ресурсы приложения при одновременной работе с базой данных и внешними сервисами.
